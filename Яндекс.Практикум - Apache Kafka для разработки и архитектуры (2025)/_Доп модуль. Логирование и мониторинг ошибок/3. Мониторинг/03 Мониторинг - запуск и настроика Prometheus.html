Push vs Pull модели

Есть система мониторинга, совмещающая подходы White-box и Black-box. Называется Prometheus! Она позволяет как экспортировать общее количество http-запросов, полученных приложением, так и собирать стандартные системные метрики.
Существуют Push и Pull модели мониторинга:
  • Push-модель — когда у вас есть централизованный сервер, на который распределенные агенты активно пушат метрики. В Push-модели вам нужно отдельно настраивать каждый сервер, который вы хотите мониторить, устанавливая на него специальный агент мониторинга. При таком подходе сервер мониторинга занимается своей основной задачей — хранит метрики и управляет их жизненным циклом, спокойно ожидая, пока в его базу данных что-нибудь положат. Основная модель работы системы мониторинга Zabbix — Push-модель.
  • Pull-модель – подход, набравший популярность с приходом в нашу жизнь платформ оркестрации контейнеров. В этом случае сам сервер мониторинга находит эндпоинты экспортеров для сбора метрик.
Эндпоинт (англ. endpoint) — в текущем контексте это URL для http-запросов метрик. По соглашению, приложение запускает http-сервер на служебном порту и отдаёт метрики на GET запросы к /metrics.
Экспортёр (англ. exporter) — библиотека для приложения или отдельный процесс на сервере, выполняющие публикацию (экспорт) актуальных метрик. Экспортёры могут предоставлять внутренние метрики приложения (метрики времени обработки пользовательских http-запросов), служить интеграционной прослойкой (из логов Nginx извлекать время обработки запроса и частоту ошибок) или выступать агентом для мониторинга сервера (Node Exporter).
Pull-модель отлично показывает себя в эфемерных средах вроде Kubernetes, когда количество точек мониторинга изменяется с течением времени. Для мониторинга серверов эта модель тоже подходит, но нужно будет озаботиться автоматизацией добавления новых серверов или удаления неактуальных из конфигурации.
В особых случаях для получения метрик понадобятся промежуточные серверы, работающие по push-модели. Например, когда целевые серверы находятся за файерволом с политикой, запрещающей двунаправленные соединения.

Как вам задача?
Система мониторинга Prometheus в основном работает по pull-модели. В конфигурации сервера указывается список целей для сбора метрик и периодичность опроса.

Архитектура Prometheus

Основные компоненты Prometheus это:
  • сам сервер, выполняющий периодический опрос экспортеров,
  • база данных временных рядов (англ. time series database, TSDB) — хранилище метрик,
  • алерт-менеджер для отправки оповещений.
Данные метрик в Prometheus хранятся в базе данных в виде временных рядов (англ. time series) — численных значений измеряемой характеристики и временной метки каждого измерения. С метрикой ассоциируется имя и набор лейблов — пар ключ-значение с дополнительной информацией о происхождении метрики. Временные ряды позволяют эффективно анализировать изменения метрики с течением времени, а лейблы однозначно определяют происхождение данных: сервер-источник, имя приложения, название окружения.
Интерфейсом к такой базе данных служит язык PromQL — язык запросов Prometheus. Внешний клиент, будь то человек или приложение отрисовки графиков, будет выполнять запрос на языке PromQL для получения данных. Посмотрите, как выглядит простой запрос для получения общего количества HTTP-запросов на сервере фронтенда тестового окружения:
http_requests_total{instance="frontend", env="test"}
Такой запрос выдаст временной ряд, связанный с метрикой http_requests_total и значениями лейблов в фигурных скобках.

Запуск Prometheus

Для установки Prometheus на стандартной системе Ubuntu вам потребуется выполнить ряд шагов, которые отличаются от процесса установки с использованием Helm и Kubernetes. Вот основные шаги:
  1. Обновление системы: Для начала обновите список пакетов и установите последние версии пакетов:

    BASH

     sudo apt-get update
 sudo apt-get upgrade
  2. Скачивание и установка Prometheus:
    • Сначала скачайте последнюю версию Prometheus с официального сайта. Вы можете найти ссылку на последнюю версию в разделе загрузок.
    • Распакуйте скачанный архив:

    BASH

         tar xvfz prometheus-*.tar.gz
     cd prometheus-
    • Это создаст директорию с исполняемыми файлами Prometheus и примерами конфигурационных файлов.
  3. Настройка Prometheus:
    • Вы можете настроить Prometheus, редактируя файл prometheus.yml. Для начала можно использовать стандартные настройки.
  4. Запуск Prometheus:
    • Запустите Prometheus из его директории:

    BASH

         ./prometheus --config.file=prometheus.yml
  5. Проверка работоспособности:
    • По умолчанию, Prometheus будет доступен на порту 9090. Откройте браузер и перейдите по адресу http://<IP-адрес-вашего-сервера>:9090, чтобы убедиться, что Prometheus работает.
  6. Настройка Service Discovery и Targets:
    • Для добавления целей (targets) в Prometheus, вам потребуется отредактировать файл prometheus.yml, добавив в него информацию о вашем бэкенде или экспортерах.
  7. Установка как службы:
    • Чтобы Prometheus запускался автоматически при старте системы, его можно установить как системную службу. Создайте файл службы systemd и настройте его для автоматического запуска Prometheus.
Этот процесс является базовым и может потребовать дополнительной настройки в зависимости от ваших конкретных требований и конфигурации системы.

Prometheus-экспортёр для бэкенда

Node Exporter - это инструмент для мониторинга серверов, который собирает информацию о работе операционной системы и аппаратном обеспечении. Он предоставляет данные в формате, который Prometheus может собирать и анализировать
Для установки node-exporter на Ubuntu и замены подхода с использованием kubectl port-forward для проверки эндпоинтов, выполните следующие шаги:
  1. Установка Node Exporter:
    • Сначала скачайте последнюю версию node-exporter с официального сайта Prometheus Node Exporter.
    • Распакуйте архив и запустите node-exporter:

    BASH

         bashCopy code
     tar xvfz node_exporter-*.tar.gz
     cd node_exporter-*
     ./node_exporter
  2. Проверка работы Node Exporter:
    • node-exporter по умолчанию запускается на порту 9100. Чтобы убедиться, что он работает, откройте браузер и перейдите по адресу http://<IP-адрес-вашего-сервера>:9100/metrics.
  3. Просмотр метрик:
    • При переходе по указанному адресу вы увидите список метрик, собираемых node-exporter. Эти метрики будут в формате, понятном для Prometheus. Примеры метрик:

    BASH

         bashCopy code
     # HELP node_cpu_seconds_total Seconds the CPUs spent in each mode.
     # TYPE node_cpu_seconds_total counter
     node_cpu_seconds_total{cpu="0",mode="idle"} 4.194304e+06
     node_cpu_seconds_total{cpu="0",mode="system"} 8.2182e+04
     ...
  4. Добавление Node Exporter в Prometheus:
    • Чтобы добавить node-exporter в качестве цели для Prometheus, вам потребуется отредактировать файл prometheus.yml и добавить туда node-exporter в качестве target.
    • Пример конфигурации:

    YAML

         yamlCopy code
     - job_name: 'node'
       static_configs:
       - targets: ['<IP-адрес-node-exporter>:9100']
  5. Перезапуск Prometheus:
    • После изменения конфигурации Prometheus, перезапустите Prometheus, чтобы он начал собирать метрики с node-exporter.
Далее научим Prometheus собирать метрики.

Prometheus Service Discovery

Prometheus Service Discovery — это механизм, который автоматически находит и конфигурирует цели для мониторинга. Это особенно полезно в динамичных средах, где IP-адреса и хосты могут часто меняться.
Конфигурация сервера Prometheus определяется в YAML-формате, по соглашению в файле prometheus.yml.
В случае статических конфигураций (как в вашем случае), вы вручную добавляете цели в prometheus.yml. Однако, в более динамичных средах, как Kubernetes, Prometheus может автоматически обнаруживать сервисы и экспортеры, используя Service Discovery.
В конфигурации нам важны следующие секции:
  • global — глобальные параметры, которые допустимы во всех других контекстах конфигурации. Параметры из этой секции также служат значениями по умолчанию для других разделов конфигурации;
  • scrape_configs — настройки поиска целей мониторинга.
Цели мониторинга могут быть определены явно — в scrape_configs указывается адрес и URL экспортёра:
  1. Редактирование файла prometheus.yml:
    • Откройте файл конфигурации prometheus.yml для редактирования.
    • В разделе scrape_configs, вы определите цели мониторинга и их параметры.
    global:
      scrape_interval: 15s
    
    scrape_configs:
        # Значение job_name добавляется лейблом `job=<job_name>` ко всем метрикам из этой конфигурации
      - job_name: 'example_exporter'metrics_path: '/metrics'static_configs:
          - targets: ['example.com:8080']
  1. Настройка статических целей для мониторинга:
    • Пример конфигурации для мониторинга локального сервиса:

YAML

        global:
          scrape_interval: 15s
        
        # Конфигурация для мониторинга node_exporter
          - job_name: 'node_exporter'
            static_configs:
              - targets: ['localhost:9100']
        
        # Конфигурация для мониторинга самого Prometheus
          - job_name: 'prometheus'
            static_configs:
              - targets: ['localhost:9090']
  • Здесь localhost:8080 является адресом и портом вашего сервиса, который вы хотите мониторить. 3. Применение изменений:
  • После внесения изменений в файл конфигурации, перезапустите Prometheus, чтобы изменения вступили в силу. 4. Проверка целей в Prometheus:
  • После перезапуска Prometheus, зайдите на веб-интерфейс Prometheus (обычно http://localhost:9090) и проверьте раздел Targets для убеждения, что ваша цель отображается и метрики собираются правильно. 5. Добавление аннотаций в конфигурацию сервиса (необязательно):
  • Если ваш сервис предоставляет метрики в определённом формате (например, /actuator/prometheus для Spring Boot приложений), укажите это в настройках цели:

YAML

         job_name: 'spring_boot_app'
          metrics_path: '/metrics'
          static_configs:
            - targets: ['localhost:9100']
  1. Релейбелинг и дополнительные настройки:
    • Вы можете использовать relabel_configs для более детальной настройки целей, например, для изменения лейблов или фильтрации.
    • Пример использования relabel_configs:

YAML

        yamlCopy code
        relabel_configs:
          - source_labels: [__address__]
            regex: '(.+):9100'
            target_label: instance
            replacement: '$1'
Это основной подход к настройке Prometheus
Prometheus и Node Exporter вместе: Позволяют вам создать мощную систему мониторинга, способную адаптироваться к изменяющейся инфраструктуре и обеспечивать непрерывный сбор данных о работе ваших сервисов.

Ключевые мысли урока

  • Push и Pull модели определяют способ сбора метрик
  • Экспортёр — библиотека для приложения или отдельный процесс на сервере, выполняющие публикацию актуальных метрик
  • Данные метрик в Prometheus хранятся в базе данных в виде временных рядов, а интерфейсом к такой базе данных служит язык PromQL
  • Цели мониторинга в Prometheus могут быть определены явно, а могут добавляться автоматически с помощью механизма Service Discovery
  • Полученные метрики лучше оформить в виде графиков в Grafana
